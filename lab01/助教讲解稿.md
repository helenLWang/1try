# 向助教讲述时用的完整说法

不要按「第一问、第二问」报菜名。把屏幕上的结果当成证据，按下面这一条故事讲完。大约三到五分钟。

---

我先建立一条到课程 Kafka 的 SSH 隧道：`ssh -L 9092:localhost:9092 tunnel@128.2.220.123 -NT`。课程不让直连远端 9092，这条命令把我电脑上的 9092 转到 broker 自己的 localhost:9092。所以后面 Python 和 kcat 都连 `localhost:9092`，Kafka 看起来像在本地。`kcat -L` 能列出我的 topic `lab01-helenlwang` 和组项目会用的 `movielog1`，说明隧道是通的。

Kafka 在这门课里应当被理解成一本只能追加的公共日志，而不是读完就消失的队列。Topic 是这本日志的名字。Partition 是一卷；我的实验 topic 只有一卷。Offset 是这一卷里每一行的整数地址，由 broker 在写入时分配。我的 producer 写了 20 条城市温度，分到的 offset 是 0 到 19。下一条将被写成 20，这个位置叫 high watermark。

Consumer 属于一个 group 时，可以把自己处理到的 offset 提交回去。进程断开以后，消息仍然留在 broker 的日志里（在保留期内）。重连后 group 从上次提交位置的下一行继续，所以既不会因为「有人读过」就丢数据，也不会在正常情况下把已经处理过的再处理一遍。若我故意要重放，就换一个 group、或者调用 seek、或者在 kcat 里指定 `-o`。

`auto_offset_reset` 不是「从哪里开始」的通用旋钮。它只在这个 group 还没有有效的已提交 offset 时生效，而且只能选两个端点：`earliest` 从还保留的最老一行开始，我这里是 0；`latest` 跳到水位线只等新消息；`none` 则直接报错。`earliest` 的代价是可能重复处理历史；`latest` 的代价是故障期间的数据你主动放弃。我的 consumer 用 `earliest`，所以 20 条全部读回，写进了 `kafka_log.csv`。

真实系统需要从中间开始：重放最近若干条、或从崩溃点稍往前一点重新处理。这是 `auto_offset_reset` 做不到的。我先读 `beginning_offsets` 和 `end_offsets`，得到可读范围 0 到 19，然后 seek 到三个铺开的点。从 0 读，这是 `earliest` 自己就能到的。从 10 读，这是中点，必须 seek。从 18 读，这是「最后两条」；`latest` 会到 20，那里现在是空的，所以 18 也必须 seek。

最后用 kcat 做同一件事。`-o beginning -c 5` 从 0 打出五条；`-o 8 -c 5` 从绝对地址 8 打出五条，第一条是 Pittsburgh、64，和 Python consumer 在 offset 8 看到的一样。这说明 offset 是跨客户端稳定的地址。`-e` 让它在日志末尾退出，否则会一直等新消息。

组项目里同一套地址机制读的是 `movielog1`：一行里有时间、数字用户 ID、字符串电影 ID。详情再问 `http://128.2.220.123:8080/user/<id>` 和 `/movie/<id>`。除了本 lab 写自己的 `lab01-...`，平时只读。
